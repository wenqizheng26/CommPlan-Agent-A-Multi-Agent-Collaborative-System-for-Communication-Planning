# 长期路线（M1 之后）

状态：设计，未实施。条目和优先级来自 Claude 与 Codex 2026-10-02 双方审核通过的提升清单（S2-v1 第 3 节，L1–L12），事实按 2026-10-03 的勘误更正；“建议顺序”一节是本文新整理的，需双方另行审核。M1（2026-10-24）之前不按本文改代码；开工前每一项再单独定范围、写测试、经双方审核。

## 目标形态

本机离线的通信筹划助手，兼作单位内部工具和科研原型。用户用自然语言提出需求；系统追问缺项或给出可追溯的默认值，用户确认后由程序做确定性专业计算，模型核查并解释，最后由用户在同口径的方案之间选择。演进顺序是：审核过的计算引擎 → 公式与事实入库 → 有限候选比较与选型 → 组网与覆盖（见 `docs/requirements.md`、`ACCEPTANCE_M1.md`）。

不做的事：不默认综合评分权重；不把库里有公式说成已经能用于生产计算；不把链路余量说成吞吐、误码率或可用率的保证。

## 分工原则

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 模型 | 理解需求、提出计划和子任务、选候选、解释结果 | 产生专业数值 |
| 规则 | 校验计划（准入、量纲、适用条件）、确定性计算、重放核对 | 猜用户意图 |
| 检索 | 给出可核查的公式卡、资料和出处 | 直接决定计算路径 |

每加一个环节都要写明三件事：谁提出、谁核对、失败时退到哪里。

## 建议顺序

本节是本文新整理的，S2-v1 只定了“L1 第一优先”和各项定位。

1. **M1 后第一批**：L1 与 L9 分阶段一起做（子任务拆分和有界总控是同一件事的两面，L1 的 3–5 天不含完整 L9），同时做 L2、L3、L4（工作量各自另算，不并入 L1 的 3–5 天）。
2. **第二批**：先做 L8 的回归基线，再做 L7 的口径迁移；L5、L6 随后。L5 依赖 L3、L4 积累的卡。
3. **长期**：L10，取决于能拿到的真实数据。
4. **可选**：L11（依赖外场条件）、L12（核对接口后再定）。

## 共同要求

- 每条新知识都要有来源、适用范围和独立算例。卡接入计算不等于现实场景达标；特殊传播条件和实际数据仍要单独验证。
- 改报告合同、计算口径或常数时升版，旧任务和历史结果按原版本保留和展示。
- 真实模型只在固定用例和留出集上验证过，不能说成任意表述都能通过；每次报告通过率时写明提交号、模型版本和用例集。
